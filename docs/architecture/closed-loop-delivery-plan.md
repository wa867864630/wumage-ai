# 对话应用平台分阶段交付计划

版本：0.1，2026-10-20。状态：评审后的开发基线；本文件不表示以下待办已实现。

目标：应用首版可以简单，但从发现、创建、配置、发布、使用到查询结果、错误恢复，每条已开放路径必须走得通。每次交付一条可验收的用户流程，限制同时修改的公共模块。开发约束见 [开发与版本规范](development-and-versioning.md)，类型契约沿用 [应用类型扩展协议](application-type-extension.md)。

## 1. 现状与必须先解决的风险

| 已有基础/发现 | 对下一步的影响 |
| --- | --- |
| 课程模板创建、独立配置/问法、发布/回滚、对话发现和功能入口已实现 | 保持为兼容基线，不为了接新类型整体重写 |
| 最近一次已记录验证为150项后端测试及前端状态回归 | 是已测范围的证据，不等于所有新场景或真实浏览器已验收；本轮只写规范，不重报测试 |
| 当前目录不是Git仓库 | 现有发布快照只能恢复配置，不能恢复源码；先建立源码基线与恢复副本 |
| 当前执行环境生产构建受spawn EPERM限制，旧dist未更新 | 开发服务可继续验证，但正式发布必须在可构建环境产出并验收对应产物 |
| 类型摘要覆盖清单、Schema和人工实现版本号，未覆盖实际实现字节 | 不能视为完整代码包摘要；类型升级前补构建清单和真实实现摘要 |
| 前端Workspace及后端应用路由承担越来越多职责，能力信息仍有课程专用逻辑 | 增量提取类型能力声明；保留旧适配器，避免继续给全局路由堆每种业务分支 |
| 业务任务、填写进度主要在当前页面内；表单/审批运行时未实现 | 不先承诺刷新恢复、在途审批或任意业务创建；这些是新增业务写入的前置条件 |

不承诺仅靠文档达到零回归。采用契约约束、功能隔离、回归证据和经过演练的恢复路径降低风险，任何一项未完成均保留真实状态。

## 2. 实施顺序与开放条件

| 阶段 | 用户得到的完整流程 | 本阶段不扩张的范围 | 开放门槛 |
| --- | --- | --- | --- |
| P0 版本与兼容基线 | 现有课程场景可复验、源码和配置均可定位与恢复 | 新业务、编辑器重写 | 源码基线、变更清单、旧链路回归、恢复方案；正式部署另需构建及浏览器验收 |
| P1 对话任务与创建引导 | 找不到应用→按身份引导→保存建设需求/创建已安装类型→继续完善→回原任务 | 尚未安装类型的假运行应用 | 类型/权限/发布状态区分正确；任务草稿可恢复；创建同键不重复 |
| P2 简单表单登记 | 模板创建登记应用→配置字段→发布→用户提交→查看结果→管理员按权限查看记录 | 审批、动态DDL、复杂关系 | 提交、记录、查询、权限、并发和异常恢复全链路通过 |
| P3 单级请假 | 对话发现/创建请假应用→发布→申请→审批→查进度→结束 | 会签、并行、多级条件流、自动业务实例迁移 | 单级审批及各终态完整，审批人来自真实可验证目录，申请/任务/审计事务一致 |
| P4 统一创建中心 | 模板/复制/AI文字三种入口→同一需求与草稿→差异/校验→发布→继续原任务 | 文档解析、任意执行代码 | 人工操作可独立完成，AI失败不影响草稿，复制范围和权限明确 |
| P5 文档辅助创建 | 上传支持格式→提取来源与不确定点→确认→同一草稿/发布流程 | 扫描件OCR、任意文件类型、自动采纳规则 | 格式/大小/保留期受控，来源可追溯，取消/重复上传/解析失败可恢复 |
| P6 跨应用与维护 | 填写请假→临时查课表→返回原草稿；待办、实例维护、停用归档可用 | 不受控跨应用写入、任意类型市场 | 跨任务恢复和越权测试通过；停用不丢在途工作；上一稳定版恢复演练通过 |

阶段按依赖顺序交付，不按“先把所有按钮画出来”交付。每个阶段允许拆为小改动，但正式开放需要完成整条流程。P0未取得正式构建证据时，可以在隔离开发环境推进后续工作，不得把开发服务验证记为生产发布。

## 3. P0：保护已有功能，再允许新增能力

1. 确认源码目录及Git归属，初始化或接入正确仓库，审阅忽略规则后建立基线提交；不把密钥、本地配置、数据库内容或依赖缓存提交。远程推送另按实际授权执行。
2. 保存当前源码提交、依赖锁文件、数据库修订0006、已发布类型与应用版本、配置摘要及验证报告的关联清单。数据库备份包含恢复所需的数据与结构，验证可读取及可恢复；只有摘要不等于有备份。
3. 建立必须保持的兼容清单：登录退出、原课程接口、模板创建、草稿/发布分离、问法审核、幂等重试、应用/租户隔离、对话锁定切换、管理员导航。
4. 将现有脚本组织为按变更影响选择的检查入口，保留完整回归入口。不靠固定测试数量判断成功，不隐藏跳过项。
5. 固定前后端、Schema及类型包的构建对应关系；显示可核对的版本信息。补充原浏览器操作验收，在可正常构建环境执行生产构建。
6. 做一次开发/预发恢复演练，核对恢复后的登录、查询和配置读取；记录代码、数据库与应用配置各自的恢复边界。

开发出口：可恢复源码基线和旧闭环证据。部署出口：构建成功、产物校验、浏览器核心操作验收、兼容数据库范围和恢复说明齐备。未建立Git基线或恢复副本时，不把临时文件副本称为已完成版本管理。

## 4. P1：先把“没找到→继续办理”的任务接住

用持久化任务草稿承接建设意图，而不是只记住聊天文本。任务最少绑定tenant、owner、task_id、目标业务、目标应用/类型（允许尚未确定）、任务种类、当前步骤、修订、来源、已确认事实、缺项及最后保存时间。敏感业务字段按最小必要保存，授权和保留期随任务种类定义。

建设需求和可运行应用分开：请假类型未安装时，只能保存“请假应用建设需求”，不能套课程模板产生可发布的请假空壳。类型可用后，再将需求显式转换为应用草稿，并保留来源关系。

建议任务状态：收集需求、待选择方式、编辑草稿、待补全、待校验、待确认、执行中、结果待核对、完成、取消。具体状态由服务端控制；写入结果待核对时保留原命令号，不能用“重来”产生重复实例。

用户验收：

- 普通用户说“我要请假”，没有可用服务时获得真实说明及已配置的求助入口，不出现管理员创建按钮；没有配置联系人时不编造联系方式。
- 管理员接着说“创建这个应用”，指向上一条已确定的建设意图；多个可能对象则确认目标。
- 已安装类型提供可用模板创建；未安装类型显示“保存需求，等待能力接入”，只开放可完成的动作。
- 刷新、重新登录后可恢复本人获授权任务；任务失效、权限变化、来源被归档时明确解释。
- 已有同类草稿/应用先展示候选供管理员确认，不自动合并，也不以名称判定两个应用必然相同。

## 5. P2：简单表单也必须有真实的数据闭环

首个类型为简单登记：文本、长文本、数字、日期、单选、多选、布尔；支持组件选择、顺序、必填、校验及有限响应式分栏。暂不支持脚本、联表公式、任意数据源和字段配置自动DDL。

用户路径：创建登记应用→设置字段与访问角色→预览合法/非法输入→发布→填写→确认提交→得到记录编号→列表与详情查看。管理员按授权查看记录；首版可不提供删除、导出和批量操作，但不能展示这些无执行能力的按钮。

申请数据、应用草稿、聊天任务分开保存。每条业务记录固定所属应用和提交时发布版本；更改表单不改变旧记录解释。服务端验证类型、范围和行权限，页面隐藏字段不是授权。提交和审计在同一事务，重试不多一条记录。

出口：有效/无效提交、双击、超时重试、刷新恢复、本人/他人、管理员范围、跨应用跨租户、发布前后旧记录查看全部通过。

## 6. P3：单级请假作为审批能力的完整样板

最小业务字段：请假起止、原因及必要身份引用；身份、申请人、组织由服务端确定。审批人为组织内已验证且具有办理权限的用户，先支持人工选择一个审批人；无可靠人员目录或有效审批人则阻止发布。平台不能把任意填写的姓名视为可执行人员绑定。

首版采用独立请假业务适配器，复用P2字段与组件，不先开发通用工作流引擎。申请、审批任务、状态事件及关键审计需事务一致；并发审批只允许一个合法状态迁移。最小状态为草稿、待审批、已通过、已拒绝、已撤回；撤回仅限未完成审批且策略允许时。

用户路径：对话打开服务→填写/暂存→确认提交→获得申请号→审批人在待办查看并处理→申请人看到最终状态及记录。通知失败不撤销已成功提交，待办为权威；通知尚未接入时明确通过待办查询，不声称短信/邮件已发送。

发布更新只影响新发起实例；在途申请固定原release与流程定义。应用停用的最低规则是停止新发起，在途办理沿原策略及当前权限继续；没有在途处理策略时不得开放停用入口。

出口：批准、拒绝、撤回、重复提交、并发审批、超时核对、无效审批人、权限撤销、跨应用访问、发布更新后旧任务办理均有证据。只生成流程图不算审批闭环完成。

## 7. P4/P5：丰富创建方式，保持同一条发布链路

先让人工模板和复制可以独立完成P2/P3，再接AI文字；AI只是提供受控提案。模板、复制、AI和文档最后统一为“确认需求→应用草稿→缺项清单→预览/模拟→明确发布→返回原任务”。不建立四套草稿或发布中心。

- 模板固定类型和模板版本、默认配置及必需绑定说明，权限和凭据不随模板自动授予。
- 复制明确来源发布或草稿修订，默认只复制设计；新实例、新修订、新审计，不复制业务数据、密钥、在途任务及历史发布身份。
- AI绑定task/application/type/draft/catalog版本与授权上限；保留手工入口、修改差异、澄清及失败恢复，不让模型直接提交或发布。
- 文档首批建议仅UTF-8文本/Markdown及可提取文本的PDF；实施时冻结确切格式和预算。扫描件/复杂表格转人工说明，来源按段落/页码展示；提取事实与管理员确认的业务规则分开。

P4出口：同一简单请假应用从模板、复制和文字描述得到合法草稿，经相同发布检查可运行。P5出口：支持格式导入、歧义确认、超时/重复上传/取消及附件清理闭环通过。不能只凭解析成功或JSON合法宣称应用可运行。

## 8. P6：跨应用任务和维护

P1负责单任务恢复，P6增加任务切换栈：请假草稿暂停→课程查询临时任务→回到原草稿步骤。切换不丢数据，“这个”“刚才那个”引用task/object而非最近出现的字符串；目标不唯一必须澄清。

数据列表、详情、待办、已办、失败状态和必要审计共用类型能力声明。扩展导出、批量操作、通知和归档时分别交付完整场景，不默认开放所有操作。定时通知和外部调用经Outbox/幂等机制，业务完成与通知送达分开显示。

## 9. 所有阶段共用的验收与止损规则

| 验收维度 | 必须证明 |
| --- | --- |
| 主路径 | 新用户能找到入口、知道下一步、完成操作、看到结果、重新查询 |
| 异常 | 空列表、加载失败、无权限、版本冲突、超时、结果待核对各有明确反馈及可用下一步 |
| 一致性 | 对话/按钮/页面调用同一业务命令，后端重复授权；用户看见的状态来自真实持久结果 |
| 隔离 | 同名应用、不同用户、不同租户、旧消息按钮、迟到响应不串用数据或动作 |
| 兼容 | 旧课程闭环、旧发布快照和保留的旧客户端路径继续有效；新类型未启用不影响旧类型 |
| 版本 | 每项证据绑定源码提交/产物、数据库修订、类型/Schema及应用发布版本 |
| 体验 | 明确状态、有限主操作、未保存保护、正确焦点/键盘及窄屏可用；DOM测试之外做浏览器验收 |

新增能力按租户及类型逐步启用，开关在服务端控制发现与执行，不能只隐藏前端按钮。停用发现不等于删除任务或取消已提交事务；具体在途行为按类型策略执行。

出现旧核心链路失败、越权、跨应用串数据、重复业务写入、未知状态被当作成功时，停止扩大开放范围，优先修复或关闭新入口。恢复执行按 [版本规范](development-and-versioning.md)，不自动逆向迁移数据库。

## 10. 下一次实施的明确范围

下一批先做P0：源码恢复基线、版本/构建清单及现有闭环检查组织；同时将“建设需求任务”和“可运行应用”的契约、状态及权限确定为P1输入。不要在这一批同时改造表单、审批、文档解析和全部路由。

阶段交付说明固定包含：本次完成的用户流程、明确边界、版本关联、实际测试、尚未验收内容、恢复办法和下一阶段。未验证项写“待验收”，不能用“应该兼容”代替结果。
