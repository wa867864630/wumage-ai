# 对话应用平台分阶段交付计划

版本：0.3，2026-10-20。状态：P1—P6首版开发与回归，真实浏览器待用户验收；不表示生产发布。当前实现和操作以[运行手册](../runbooks/assistant-requirements.md)顶部为准，下文早期风险表保留评估语境。

本轮范围：需求管理与原子创建；三类应用的配置/发布/使用；单级请假办理；模板/同类型设计复制/受限AI/文本说明创建；本人草稿暂停、课程查询、明确返回续填；启用/停用/归档。JSON仍经精确类型、权限和业务校验，AI不执行发布。数据库递增到0011，保留0006—0010恢复边界。通用流程引擎、组织目录、PDF/OCR、附件、通知、导出不在首版开放范围。

目标：应用首版可以简单，但从发现、创建、配置、发布、使用到查询结果、错误恢复，每条已开放路径必须走得通。每次交付一条可验收的用户流程，限制同时修改的公共模块。开发约束见 [开发与版本规范](development-and-versioning.md)，类型契约沿用 [应用类型扩展协议](application-type-extension.md)。

## 2. 实施顺序与开放条件

| 阶段 | 用户得到的完整流程 | 本阶段不扩张的范围 | 开放门槛 |
| --- | --- | --- | --- |
| P0 版本与兼容基线 | 现有课程场景可复验、源码和配置均可定位与恢复 | 新业务、编辑器重写 | 源码基线、变更清单、旧链路回归、恢复方案；正式部署另需构建及浏览器验收 |
| P1 对话任务与创建引导 | 找不到应用→按身份引导→保存建设需求/创建已安装类型→继续完善→回原任务 | 尚未安装类型的假运行应用 | 类型/权限/发布状态区分正确；任务草稿可恢复；创建同键不重复 |
| P2 简单表单登记 | 模板创建登记应用→配置字段→发布→用户提交→查看结果→管理员按权限查看记录 | 审批、动态DDL、复杂关系 | 提交、记录、查询、权限、并发和异常恢复全链路通过 |
| P3 单级请假 | 对话发现/创建请假应用→发布→申请→审批→查进度→结束 | 会签、并行、多级条件流、自动业务实例迁移 | 单级审批及各终态完整，审批人来自真实可验证目录，申请/任务/审计事务一致 |
| P4 统一创建中心 | 模板/复制/AI文字三种入口→同一需求与草稿→差异/校验→发布→继续原任务 | 文档解析、任意执行代码 | 人工操作可独立完成，AI失败不影响草稿，复制范围和权限明确 |
| P5 文档辅助创建 | 上传支持格式→提取来源与不确定点→确认→同一草稿/发布流程 | 扫描件OCR、任意文件类型、自动采纳规则 | 格式/大小/保留期受控，来源可追溯，取消/重复上传/解析失败可恢复 |
| P6 跨应用与维护 | 填写请假→临时查课表→返回原草稿；待办、实例维护、停用归档可用 | 不受控跨应用写入、任意类型市场 | 跨任务恢复和越权测试通过；停用不丢在途工作；上一稳定版恢复演练通过 |

阶段按依赖顺序交付，不按“先把所有按钮画出来”交付。每个阶段允许拆为小改动，但正式开放需要完成整条流程。P0未取得正式构建证据时，可以在隔离开发环境推进后续工作，不得把开发服务验证记为生产发布。

## 3. P0：保护已有功能，再允许新增能力

1. 确认源码目录及Git归属，初始化或接入正确仓库，审阅忽略规则后建立基线提交；不把密钥、本地配置、数据库内容或依赖缓存提交。远程推送另按实际授权执行。
2. 保存当前源码提交、依赖锁文件、实际数据库修订（现为0007）、已发布类型与应用版本、配置摘要及验证报告的关联清单。数据库备份包含恢复所需的数据与结构，验证可读取及可恢复；只有摘要不等于有备份。旧0006八表与0007九表恢复范围分别记录。
3. 建立必须保持的兼容清单：登录退出、原课程接口、模板创建、草稿/发布分离、问法审核、幂等重试、应用/租户隔离、对话锁定切换、管理员导航。
4. 将现有脚本组织为按变更影响选择的检查入口，保留完整回归入口。不靠固定测试数量判断成功，不隐藏跳过项。
5. 固定前后端、Schema及类型包的构建对应关系；显示可核对的版本信息。补充原浏览器操作验收，在可正常构建环境执行生产构建。
6. 做一次开发/预发恢复演练，核对恢复后的登录、查询和配置读取；记录代码、数据库与应用配置各自的恢复边界。

开发出口：可恢复源码基线和旧闭环证据。部署出口：构建成功、产物校验、浏览器核心操作验收、兼容数据库范围和恢复说明齐备。未建立Git基线或恢复副本时，不把临时文件副本称为已完成版本管理。

## 4. P1：先把“没找到→继续办理”的任务接住

当前已实现的首段操作见 [建设需求运行手册](../runbooks/assistant-requirements.md)。以下P1-A/B/C为后续实施顺序，不是现有接口承诺。

0008实施补充：已实现需求详情/编辑/修订审计、状态筛选分页、活动额度、未保存保护、迟到读取隔离、持久命令核对、课程模板创建确认和原子转换、恢复目标配置、读取真实发布进度及返回应用使用。下列细项仍作为验收依据；关闭标签页前未发送的输入不会自动成为服务端草稿，跨应用任务栈、其他业务类型和四种完整创建方式仍按后续阶段实施。具体命令与边界见运行手册，不把P1课程链路等同P2—P6全部完成。

用持久化任务草稿承接建设意图，而不是只记住聊天文本。任务最少绑定tenant、owner、task_id、目标业务、目标应用/类型（允许尚未确定）、任务种类、当前步骤、修订、来源、已确认事实、缺项及最后保存时间。敏感业务字段按最小必要保存，授权和保留期随任务种类定义。

建设需求和可运行应用分开：请假类型未安装时，只能保存“请假应用建设需求”，不能套课程模板产生可发布的请假空壳。类型可用后，再将需求显式转换为应用草稿，并保留来源关系。

建议任务状态：收集需求、待选择方式、编辑草稿、待补全、待校验、待确认、执行中、结果待核对、完成、取消。具体状态由服务端控制；写入结果待核对时保留原命令号，不能用“重来”产生重复实例。

用户验收：

- 普通用户说“我要请假”，没有可用服务时获得真实说明及已配置的求助入口，不出现管理员创建按钮；没有配置联系人时不编造联系方式。
- 管理员接着说“创建这个应用”，指向上一条已确定的建设意图；多个可能对象则确认目标。
- 已安装类型提供可用模板创建；未安装类型显示“保存需求，等待能力接入”，只开放可完成的动作。
- 刷新、重新登录后可恢复本人获授权任务；任务失效、权限变化、来源被归档时明确解释。
- 已有同类草稿/应用先展示候选供管理员确认，不自动合并，也不以名称判定两个应用必然相同。

### 4.1 先修复首段的恢复与管理缺口：P1-A

| 当前不足 | 下一批具体处理 | 完成依据 |
| --- | --- | --- |
| 保存后的需求只能看或取消，缺少修改入口 | 增加本人详情、修订保护的名称/说明编辑；旧版本记录可追溯；取消状态不可直接修改 | 两端同时编辑仅一个成功，另一端保留输入并展示服务端新修订 |
| pending_capability是保存状态，未表达实际能力是否可用 | 保留既有状态语义；另返回实时、按权限计算的可用动作和阻塞原因 | 安装/禁用类型后重新读取即可变化；不批量改写需求历史，不因标题自动认定类型 |
| 当前只检查收起，换页/新对话/刷新可能丢未保存内容 | 统一dirty与离开保护；已保存内容从服务端恢复；待核对命令独立处理 | 切换、取消离开、刷新、会话过期、迟到响应分别验证；不把自动填入提示误称已保存 |
| 列表尚未区分首次加载、加载失败和真实空列表 | 明确loading/error/empty/data，失败保留上次数据并标记未更新；取消过期读取 | 首次GET失败不显示“暂无需求”；旧GET不得覆盖刚保存/取消的较新修订 |
| 保存命令主要依赖sessionStorage，关标签页可能丢请求号 | 保留当前同号重试；增加本人命令结果核对入口，与持久命令记录关联；本地待核对信息只保存必要引用 | 丢响应、刷新、重新登录可查命令结果；查不到不推断成功；不以内容相似作为幂等键 |
| 当前100条上限包含已取消记录，取消不能释放额度 | 增加状态筛选、分页；活动额度与历史保留分开；容量策略单独迁移并保留幂等历史 | 达限提示有真实可完成下一步；不得提示“取消即可释放”却仍按全部记录计数 |

需求管理先保持tenant+owner隔离。管理员角色不自动获得其他管理员的需求；交接、组织可见性和保留期清理另行定义，不通过列表放宽权限解决协作。

### 4.2 接通已安装类型的创建任务：P1-B

先用现有课程类型走通，不为请假等未安装类型编造运行能力。用户流程固定为：打开需求/直接表达创建意图 → 查看已授权的现有应用候选 → 选择继续已有应用或新建 → 确认精确类型与模板 → 预览创建摘要 → 确认创建 → 进入该实例配置。

1. 服务端返回本人可访问应用及可创建类型；普通用户不能借“没有匹配”枚举未发布、无权应用或建设需求。可公开的说明只描述当前身份不可用，不披露对象存在性。
2. 类型选择以注册能力为准，名称/描述只供检索。请假需求不能映射课程类型；若管理员改变建设目标，先显式修改需求，再确认类型。未知业务允许保留描述，不要求路由必须猜出类型。
3. P1-B仅开放已安装类型的现有模板。返回创建方式、可用状态与原因；未实现方式不进入确认步骤。四种方式最终复用同一实例/草稿/发布机制，按P4/P5分别开放。
4. 确认摘要绑定需求修订、类型精确版本/摘要、模板版本/摘要、应用名称与权限范围、命令号。重新授权或摘要变化后旧确认失效；AI不得替用户确认。
5. 在同一事务中完成现有ApplicationStore创建、需求来源关联、创建任务推进及审计；复用同一创建服务而非额外调用一次HTTP。若暂时无法原子完成，先实现服务内事务入口再开放转换，不能靠前端串两个请求伪造原子性。
6. 同一建设任务首次转换只产生一个目标应用；同号同参返回同一结果，同号异参拒绝。并发取消/编辑与转换互斥；转换后需新建另一实例时，显式发起新的创建任务。
7. 创建结果持久返回application_id、task_id、来源和配置入口；丢响应通过命令号核对。已创建但配置页面加载失败时显示“应用已创建，进入配置失败”，重试导航不能重建应用。

需求记录负责建设目标；创建任务负责步骤与目标引用；配置草稿和发布仍由现有ConfigStore负责。任务只保存draft revision等引用与已确认事实，不复制整套配置成为第二个真相源。现有pending_capability/cancelled记录原样可读；新增状态、关联字段和命令账本通过后续迁移添加，不改写0007。

### 4.3 完成配置、发布、回到使用：P1-C

创建后任务指向当前应用配置，展示“基础信息→配置→校验/试跑→确认发布→返回使用”。步骤完成由实际配置及发布检查得出，不能仅因点过按钮就打勾。

| 场景 | 界面与服务端行为 |
| --- | --- |
| 暂停配置或刷新 | 从已保存的任务和ConfigStore草稿恢复应用、步骤及修订；未保存输入与已保存草稿分别说明 |
| 已有发布但草稿又改动 | 同时显示当前发布与待发布修改；旧发布不自动等同本次创建任务完成 |
| 试跑/发布检查失败 | 展示可定位的阻塞项，保留草稿，修正后重验；不跳到成功页 |
| 发布请求超时 | 保留原发布命令，先核对结果；未确认前不产生新发布命令或显示已发布 |
| 发布成功但目录暂未更新 | 使用服务端发布结果核对目录/缓存状态，可重新读取；不用重复发布刷新目录 |
| 返回原任务 | 根据持久task_id和已绑定目标恢复；若只保存了非敏感目的，可重新发起查询；将来涉及提交必须重新确认，不重放原写入 |
| 发布后本人无使用权限/缺身份绑定 | 明确“发布完成，但此身份不能使用/尚缺绑定”，引导管理员查看授权；不扩大访问范围以通过验收 |
| 取消建设任务 | 未转换时只取消需求；已创建时结束引导并保留应用草稿。删除/停用应用是另一个受控命令，不能附带执行 |

P1-C先支持一次创建任务的暂停和返回。请假填写中穿插课表查询的多任务栈仍属P6，避免以同一个“当前应用”变量承载所有任务。

### 4.4 冻结服务端动作与状态依据

下一批契约先定义对象归属、修订和操作结果，再增加UI。以下为设计约束，尚未形成已上线API：

- 每个动作声明稳定action_id、kind（read/navigation/write）、对象与精确能力版本、输入Schema、角色与行权限、前置条件、确认要求、幂等范围及结果核对方式。
- 服务端返回allowed_actions与不可用原因；前端仅通过白名单组件呈现。对话“创建这个应用”应解析到持久需求/任务ID及修订；不能继续把浏览器传来的construction_subject视为已确认对象。
- 需求工作状态、能力可用性、创建任务进度、命令执行结果分开。网络“结果未知”是客户端观察状态，数据库已提交的命令应仍可查为成功，不把业务状态改成失败后重复执行。
- 确认引用由服务端保存或校验摘要，覆盖目标、修订、参数、权限和有效期；执行时重新校验。动作过期、已取消、目标改变分别返回可恢复错误。
- 对象引用必须含真实tenant/owner/requirement/task/application作用域。历史按钮固定原目标；目标失效时解释原因并提供重新选择，不能落入当前新应用。
- 命令核对仅向本人返回必要状态与结果引用；不保存或返回模型密钥。幂等记录保留期须覆盖支持的重试窗口，到期返回明确错误，不默认为新请求。
- 扩展按新可选契约或显式版本发布；保留旧resolve/创建接口的默认行为和旧客户端兼容测试。新增字段是否可直接添加取决于客户端严格解析方式。

### 4.5 P1的交付与止损

每次仅交付A、B、C中的一段可完成操作。最低覆盖：学生/管理员、同租户他人/跨租户、空/失败/加载、同名候选、双击/并发、保存/创建/发布各阶段丢响应、刷新重登、旧消息按钮、权限撤销、取消和已有课程完整链路。构建与真实浏览器验收分别记录，不用DOM通过替代。

新增入口用服务端能力开关控制发现和执行；开关机制尚待实现。关闭转换后，已有需求仍可按权限读取和恢复，已有应用按原权限使用；不删任务、不自动降级数据库。出现越权、重复创建、跨任务串用或旧课程回归时关闭新增动作，保留读与核对路径。

## 5. P2：简单表单也必须有真实的数据闭环

首个类型为简单登记：文本、长文本、数字、日期、单选、多选、布尔；支持组件选择、顺序、必填、校验及有限响应式分栏。暂不支持脚本、联表公式、任意数据源和字段配置自动DDL。

用户路径：创建登记应用→设置字段与访问角色→预览合法/非法输入→发布→填写→确认提交→得到记录编号→列表与详情查看。管理员按授权查看记录；首版可不提供删除、导出和批量操作，但不能展示这些无执行能力的按钮。

申请数据、应用草稿、聊天任务分开保存。每条业务记录固定所属应用和提交时发布版本；更改表单不改变旧记录解释。服务端验证类型、范围和行权限，页面隐藏字段不是授权。提交和审计在同一事务，重试不多一条记录。

出口：有效/无效提交、双击、超时重试、刷新恢复、本人/他人、管理员范围、跨应用跨租户、发布前后旧记录查看全部通过。

## 6. P3：单级请假作为审批能力的完整样板

最小业务字段：请假起止、原因及必要身份引用；身份、申请人由服务端确定。评估后收窄首版审批来源为“本次发布时已认证且具有配置权限的管理员”，发布快照固定该身份，禁止自审；接管需要当前有效管理员明确说明原因并审计。组织目录和人工选人未接入，不声称已验证组织隶属关系，不接受任意填写的姓名或ID作为审批人。未来接组织目录需独立能力版本与迁移，不能静默改写在途审批来源。

首版采用独立请假业务适配器，复用P2字段与组件，不先开发通用工作流引擎。申请、审批任务、状态事件及关键审计需事务一致；并发审批只允许一个合法状态迁移。最小状态为草稿、待审批、已通过、已拒绝、已撤回；撤回仅限未完成审批且策略允许时。

用户路径：对话打开服务→填写/暂存→确认提交→获得申请号→审批人在待办查看并处理→申请人看到最终状态及记录。通知失败不撤销已成功提交，待办为权威；通知尚未接入时明确通过待办查询，不声称短信/邮件已发送。

发布更新只影响新发起实例；在途申请固定原release与流程定义。应用停用的最低规则是停止新发起，在途办理沿原策略及当前权限继续；没有在途处理策略时不得开放停用入口。

出口：批准、拒绝、撤回、重复提交、并发审批、超时核对、无效审批人、权限撤销、跨应用访问、发布更新后旧任务办理均有证据。只生成流程图不算审批闭环完成。

## 7. P4/P5：丰富创建方式，保持同一条发布链路

先让人工模板和复制可以独立完成P2/P3，再接AI文字；AI只是提供受控提案。模板、复制、AI和文档最后统一为“确认需求→应用草稿→缺项清单→预览/模拟→明确发布→返回原任务”。不建立四套草稿或发布中心。

- 模板固定类型和模板版本、默认配置及必需绑定说明，权限和凭据不随模板自动授予。
- 复制明确来源发布或草稿修订，默认只复制设计；新实例、新修订、新审计，不复制业务数据、密钥、在途任务及历史发布身份。
- AI绑定task/application/type/draft/catalog版本与授权上限；保留手工入口、修改差异、澄清及失败恢复，不让模型直接提交或发布。
- 文档首版冻结为UTF-8文本/Markdown，最多64 KiB、500行；不接收PDF或扫描件。来源显示并校验实际行号和有限原文片段；提取事实与管理员确认的业务规则分开。原文仅在请求内存中使用，不建立持久附件。

P4出口：同一简单请假应用从模板、复制和文字描述得到合法草稿，经相同发布检查可运行。P5出口：支持格式导入、歧义确认、超时/重复上传/取消及附件清理闭环通过。不能只凭解析成功或JSON合法宣称应用可运行。

## 8. P6：跨应用任务和维护

P1负责单任务恢复，P6增加任务切换栈：请假草稿暂停→课程查询临时任务→回到原草稿步骤。切换不丢数据，“这个”“刚才那个”引用task/object而非最近出现的字符串；目标不唯一必须澄清。

数据列表、详情、待办、已办、失败状态和必要审计共用类型能力声明。扩展导出、批量操作、通知和归档时分别交付完整场景，不默认开放所有操作。定时通知和外部调用经Outbox/幂等机制，业务完成与通知送达分开显示。

## 9. 所有阶段共用的验收与止损规则

| 验收维度 | 必须证明 |
| --- | --- |
| 主路径 | 新用户能找到入口、知道下一步、完成操作、看到结果、重新查询 |
| 异常 | 空列表、加载失败、无权限、版本冲突、超时、结果待核对各有明确反馈及可用下一步 |
| 一致性 | 对话/按钮/页面调用同一业务命令，后端重复授权；用户看见的状态来自真实持久结果 |
| 隔离 | 同名应用、不同用户、不同租户、旧消息按钮、迟到响应不串用数据或动作 |
| 兼容 | 旧课程闭环、旧发布快照和保留的旧客户端路径继续有效；新类型未启用不影响旧类型 |
| 版本 | 每项证据绑定源码提交/产物、数据库修订、类型/Schema及应用发布版本 |
| 体验 | 明确状态、有限主操作、未保存保护、正确焦点/键盘及窄屏可用；DOM测试之外做浏览器验收 |

新增能力按租户及类型逐步启用，开关在服务端控制发现与执行，不能只隐藏前端按钮。停用发现不等于删除任务或取消已提交事务；具体在途行为按类型策略执行。

出现旧核心链路失败、越权、跨应用串数据、重复业务写入、未知状态被当作成功时，停止扩大开放范围，优先修复或关闭新入口。恢复执行按 [版本规范](development-and-versioning.md)，不自动逆向迁移数据库。

## 10. 下一次实施的明确范围

本轮已覆盖P1—P6上述受限MVP，当前完成统一回归、契约、界面状态和恢复核对后交付用户浏览器验收。以具体草稿/应用ID恢复“刚才”，多个任务明确选择；暂不实现自动猜测的通用任务栈。若发现权限、重复写入、旧课程或恢复问题，先修复，不扩展新业务类型。后续复杂流程、组织目录、附件/导出/通知各自单独立项并遵循版本门槛。

阶段交付说明固定包含：本次完成的用户流程、明确边界、版本关联、实际测试、尚未验收内容、恢复办法和下一阶段。未验证项写“待验收”，不能用“应该兼容”代替结果。
