# 开发、交互与版本管理规范

版本：0.1，2026-10-20。适用人工与AI开发；用户明确要求优先于本规范。本规范的新增机制是开发要求，不表示仓库已经具备全部自动化能力。

## 1. 开发单位与职责边界

每个变更先明确一个用户流程、涉及的类型/角色、输入、前置条件、成功结果、错误与恢复方式。一个提交尽量只做一个可解释的改动，不把公共重构、新业务和数据库破坏性迁移混在一起。

| 层 | 负责什么 | 不得承担什么 |
| --- | --- | --- |
| 对话与任务编排 | 识别意图、澄清、能力发现、任务状态、确认与导航 | 绕过业务接口直接写表、伪造成功、根据名称授权 |
| 统一能力目录 | 类型/能力ID、版本、角色、输入、前置条件、处理器和入口声明 | 仅因AI生成了清单就标记可执行 |
| 应用类型适配器 | 配置校验、预览、发布检查、运行与迁移 | 改写其他类型的配置或扩张权限 |
| 业务服务 | 行权限、状态机、事务、幂等、业务记录及审计 | 信任客户端身份、聊天文字或模型决定权限 |
| 平台通用层 | 实例、发布、身份、模型策略、Outbox、日志与监控 | 混入每一种新业务的专属判断 |
| 前端编辑/操作组件 | 使用受控组件呈现并调用声明能力 | 任意执行模型生成代码、另造业务状态和发布机制 |

当前代码仍含课程专用逻辑，提取按使用场景逐步进行，先有兼容适配和用例再替换调用者。新增类型通过注册扩展；不能每加一个应用就把全局路由、主页面和共享配置模型改成另一种业务。

## 2. 契约与AI新增功能的交付清单

新增能力必须有：稳定ID/类型归属、精确版本、用途、输入输出、授权与数据范围、前置条件、动作种类、入口/处理器、状态/错误、确认方式、幂等范围、测试和维护说明。对话候选、功能按钮与页面应消费同一权威声明；尚未统一的旧路径通过适配保留。

AI开发新类型应提交同一扩展包：清单、配置Schema、默认值与模板、编辑器、语义验证、发布检查、业务/运行适配器、版本兼容说明、有效/反例及端到端验收。只有配置或界面时标记未实现，不注册为完整可用类型。

实现前阅读本规范、[交付计划](closed-loop-delivery-plan.md)、[类型协议](application-type-extension.md)及相关Schema。不得自行创造与既有协议冲突的第二套草稿、发布、身份或审批记录。生成应用配置遵循 [AI生成规范](ai-generation-spec.md)；AI写项目代码与业务模型生成配置是两条不同的变更链路。

## 3. 统一交互规则

- 对话用于表达和引导，详情与复杂编辑在绑定当前任务/应用的面板完成；两者使用同一命令和状态。
- 每个步骤明确正在操作的应用、对象、版本、当前进度与下一步。历史按钮绑定原对象，不随当前会话改变。
- 默认只突出当前步骤的主要操作。无权限、未安装、未发布、配置不完整分别说明；不把所有不可用情况称为“没有应用”。
- 只有真实结果才能显示已保存、已提交、已发布、已审批。正在执行、失败、冲突、结果待核对分别处理。
- 写入确认卡显示业务对象和具体变更；确认绑定服务端摘要/修订与命令ID。对象或权限变化后重新确认。
- 幂等重试保留原目标、原参数和原请求号；已确认失败可修正后发新命令，结果未知不得盲发新命令。
- 编辑离开、刷新和任务切换都有合适的保存/放弃/继续选项；合法零值、空结果与加载失败不可混淆。
- 手工操作应可完成基础流程；AI/文档失败时保留原草稿和可继续入口。不要展示没有可完成路径的主按钮。
- 沿用蓝色主题、现有表单/对话框/抽屉/状态组件；兼顾窄屏、键盘、焦点恢复与可读错误。只有复杂度确有需要才增加新的页面布局。

## 4. 版本分层，不用一个版本号代表所有内容

| 版本层 | 规则 |
| --- | --- |
| 源码 | Git提交定位完整源码；分支隔离变更，经审阅和检查后合并。不要覆盖他人未完成修改 |
| 平台发布 | 单独的语义版本及变更说明，对应不可变构建产物/摘要和源码提交；目前API显示0.2.0不等于已有同版本生产发布 |
| 产物标识 | 现打包器release_id只允许小写字母、数字、连字符；如平台版本0.3.0可映射v0-3-0，不直接把点号塞入旧协议 |
| API/动作协议 | 同一版本保留旧语义；新增字段考虑旧客户端解析方式，不能假设加字段对严格解析器总是兼容 |
| 类型实现 | type_id/type_version及实际包摘要固定实现；旧发布/任务仍引用的版本保留适配器或明确阻塞升级 |
| Schema/封装 | 独立版本线；旧DisplayConfig字符串1不得静默当成通用1.0.0，严格按类型选择校验器 |
| 模板 | 固定来源版本、类型版本及模板摘要；复制形成新实例，不继承来源实例身份与发布指针 |
| 应用配置 | draft revision乐观锁；release_id为不可变快照。应用发布不等于部署平台代码 |
| 业务任务/记录 | 固定创建/提交时应用发布及流程定义；新配置不重新解释旧记录或自动改在途审批 |
| 数据库 | Alembic递增迁移；当前0011_work_drafts_lifecycle，保留0006—0010恢复边界；已执行文件不改写；结构恢复与数据恢复单独评估 |
| AI生成 | 记录模型策略、提示词/profile/输出Schema、目录及草稿基线版本；换模型不自动改变应用发布 |

不为当前未建立的仓库编造commit、标签或发布号。建议源码流程为基线提交→功能分支→小步提交→回归/审阅→合并→发布候选→构建/验收→正式标签与产物；本地提交不等于远程备份，需约定恢复副本或受授权的远程仓库。

## 5. 类型兼容与升级

发布包清单应关联前后端构建产物、Schema、类型实现和数据契约的实际摘要，并在启动/发布检查中验证兼容。旧课程type_digest保留清单/Schema/人工实现版本范围，不重新计算历史快照。新登记与请假类型使用清单、Schema及受审阅实现的LF规范化字节摘要，请假还绑定表单依赖；共享平台和生产构建另以源码/产物摘要记录，不能拿类型摘要宣称整个平台代码没变。

新类型首版在实际实例数为0时完成后才默认开放。之后不得原地修改已发布1.0.0实现和摘要；需要先提供新版本注册、旧适配器保留及迁移/恢复证据。当前没有自动类型升级入口。配置更新仍只创建新release，不等于升级类型或变更应用启停。生命周期修订、本人填写草稿修订与应用设计修订独立，不能互相冒用。

在现有单版本注册器上直接改1.0.0清单或实现版本字符串，会导致旧实例摘要校验失败或行为悄悄变化。先建立按精确版本查找的注册机制与旧版本适配器，再新增类型版本。目标是“新版本并存”，不是重写旧快照摘要让校验通过。

升级路径固定为：兼容评估→确定性转换草稿→差异→验证/模拟→明确发布。字段改名、删除、收窄类型、审批策略变动等均检查历史引用和数据；不把版本号大小当作兼容性证明。

如果发现已发布实现的安全缺陷，不能为了保留字节不变继续执行危险逻辑；关闭或限制受影响能力，提供修复适配/迁移、审计和受影响范围说明，重新验证后恢复。

## 6. 数据库与业务事务

新增结构遵循expand→回填→核验→切换→延后清理。迁移先在隔离openGauss Schema验证实际DDL、空字符串语义、索引与锁影响，再在目标环境备份并执行；不以SQLite通过代替验证。破坏性清理另列变更，不能与首次兼容切换合并。

不修改用户现有草稿/发布来制造演示效果，不在用户应用里写验收数据。业务测试使用独立Schema，模型默认模拟。任何需要保留的用户任务、附件和业务数据都明确归属、授权、保留及清理策略。

所有对象关联都验证tenant/application/owner等实际作用域；应用名称和全局UUID都不是授权。业务写入、状态迁移及关键审计事务一致，外部通知使用Outbox等可恢复机制。模型调用和外部网络等待不占用长数据库事务。

## 7. 验证门槛

| 变更 | 最低验证 |
| --- | --- |
| 文档/规范 | 链接、示例、状态与现状一致；不虚报产品测试 |
| 简单文案/样式 | 类型检查及针对性浏览器/渲染检查，不写镜像实现的测试 |
| 对话/任务交互 | 授权目录、歧义、切换/恢复、历史动作、重复提交、迟到响应和错误路径 |
| 业务写入/流程 | 主/异常状态迁移、幂等、并发、事务、审计、租户/用户/应用隔离及端到端操作 |
| Schema/公共接口 | 有效/反例、旧样例、严格解析/未知字段、契约差异和旧调用路径 |
| 类型/迁移/共享层 | 相关专项、现有全量回归、原课程运行闭环、版本兼容及恢复演练 |
| 正式发布 | 类型/契约/回归、可复现构建与完整产物、浏览器核心路径、目标数据库版本、恢复路径 |

检查入口包括现有scripts/check.py --database、check_web.mjs、check_workbench.mjs、export_contracts.py --check、check_application_types.mjs及verify_mvp.py。命令与可选依赖用法按对应脚本和运行手册执行；真实模型验证必须作为明确授权的独立验收，不能在普通测试中意外使用本机密钥。

证据记录版本、命令、环境、结果、跳过项及限制。测试数量不是覆盖证明。模拟DOM不能代替浏览器焦点、视觉和移动端验收；生产构建失败时不得用旧dist宣称新版本已部署。

## 8. 发布与恢复

平台部署、类型升级、应用配置发布分别记录，避免一次操作同时改变所有层。上线前提供当前/目标版本和兼容数据库区间，分租户/类型开放，并监测旧查询错误、业务重复、任务失败、权限拒绝和AI用量。

| 故障范围 | 恢复动作与边界 |
| --- | --- |
| 新对话入口 | 关闭新发现/操作能力，保留旧应用直接入口及用户任务，不删除数据 |
| 应用配置 | 在校验当前权限与依赖后创建恢复发布，不改历史；不撤销已完成业务事务 |
| 新类型版本 | 停止新建/升级，保留旧版本及在途处理策略；不能把新记录强行交给旧解析器 |
| 平台代码 | 仅在前后端、API、类型和数据库兼容时切回旧产物，否则采用向前修复 |
| 数据库 | 按备份、日志和明确的数据恢复目标操作；不能默认自动降级，也不能静默丢弃新写入 |

任何出现越权、串应用、重复业务写入或核心旧链路回归的版本，停止扩大开放范围。恢复本身记录操作者、版本、影响、验证结果和在途任务处置，不只写“已回滚”。

## 9. 每次变更必须附带的交付说明

```text
用户流程及问题：
本次改动/明确边界：
涉及应用类型、角色和公共模块：
契约与版本变化/旧数据兼容：
迁移、开关及在途任务影响：
实际验证及证据（包含未验收项）：
产物/源码/数据库/应用版本关联：
失败恢复步骤与限制：
下一阶段：
```

该模板用于开发记录和审阅，不要求把技术细节堆进产品界面。变更简单时按实际影响缩写；涉及写入、版本或迁移的项目不得省略。
